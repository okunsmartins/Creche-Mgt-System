# Database Design

## Overview

PostgreSQL via Supabase. All migrations live in `supabase/migrations/` and are applied in numeric order (001–010).

## Tables

| # | Table | Description |
|---|-------|-------------|
| 1 | `reference_sequences` | Sequence counters for deterministic reference generation |
| 2 | `schools` | School record (multi-school ready via school_id) |
| 3 | `school_settings` | Key-value configuration per school |
| 4 | `profiles` | Extends `auth.users` (one-to-one) |
| 5 | `roles` | Named roles (super_admin → parent) |
| 6 | `permissions` | Granular permission strings |
| 7 | `role_permissions` | Role → Permission many-to-many |
| 8 | `user_roles` | User → Role → School assignments |
| 9 | `classes` | 8 Irish primary school classes |
| 10 | `students` | Fictional pupils with pupil payment codes |
| 11 | `parent_student_links` | Parent → Student authorised relationships |
| 12 | `parent_link_requests` | Approval flow for parent self-service linking |
| 13 | `activities` | Payable activities, trips, books, uniforms |
| 14 | `activity_class_eligibility` | Which classes can pay for which activities |
| 15 | `orders` | One order per checkout session |
| 16 | `order_items` | One row per student × activity combination |
| 17 | `payments` | Stripe payment record for each order |
| 18 | `refunds` | Full or partial refunds |
| 19 | `webhook_events` | Idempotency log for Stripe events |
| 20 | `email_notifications` | Email delivery tracking |
| 21 | `audit_logs` | Append-only admin action log |

## Key relationships

```
schools
  ├── classes (school_id)
  ├── students (school_id → class_id)
  ├── activities (school_id)
  │     └── activity_class_eligibility (activity_id → class_id)
  ├── orders (school_id)
  │     ├── order_items (order_id → student_id + activity_id)
  │     └── payments (order_id)
  │           └── refunds (payment_id)
  └── audit_logs (school_id)

profiles (auth.users.id)
  ├── user_roles (user_id → role_id)
  ├── parent_student_links (parent_id → student_id)
  └── orders.payer_profile_id

webhook_events (provider + event_id UNIQUE)
email_notifications (order_id)
```

## Monetary values

All amounts are stored as **integer euro cents** (e.g. €25.00 = `2500`). This avoids IEEE 754 floating-point rounding errors in arithmetic and aggregations.

**Never** store or accept amounts as floats. Convert at the presentation layer only.

## Reference format

| Type | Format | Example |
|------|--------|---------|
| Order | ORD-YYYY-NNNNNN | ORD-2026-000001 |
| Payment | PAY-YYYY-NNNNNN | PAY-2026-000001 |
| Order item | ITEM-YYYY-NNNNNN | ITEM-2026-000001 |
| Refund | REF-YYYY-NNNNNN | REF-2026-000001 |
| Pupil code | &lt;PREFIX&gt;-XXXXXXXX | SPP-AA111111 |

References are generated by PostgreSQL functions in a single locked transaction, preventing race conditions under concurrent load.

The pupil-code prefix is derived per school from its name (e.g. "St Peters Primary School" → `SPP`), so codes carry their own tenant's identity rather than a shared prefix. `generate_pupil_code(p_prefix)` sanitises the prefix (uppercase, alphanumeric, 2–4 chars) and falls back to `SB` if none is usable.

## Status transitions

### Order status

```
draft → pending_payment → paid → partially_refunded → fully_refunded
                       ↘ payment_failed
                       ↘ expired
draft → cancelled
```

### Payment status

```
pending → processing → paid → partially_refunded → refunded
       ↘ failed
       ↘ expired
```

### Refund status

```
pending → processing → succeeded
                    ↘ failed
pending → cancelled
```

## Soft deletes

No core entity is hard-deleted. Use `is_active = false` to deactivate students, activities and parent links. Orders and payments are never deleted.

## Row Level Security

RLS is enabled on all 20 tables. Policies enforce:
- Parents see only their own data
- Admins see all school data
- Teachers see only students in authorised classes
- Guests see only published activities and class names
- `audit_logs` is append-only (INSERT revoked from `authenticated` and `anon` roles)
- Service-role operations bypass RLS (used only server-side)

## Indexes

All foreign keys are indexed. Additional indexes on:
- `students.pupil_payment_code` (unique lookup)
- `orders.order_reference` (unique lookup)
- `orders.status` (dashboard filtering)
- `payments.provider_checkout_session_id` (webhook lookup)
- `payments.provider_payment_intent_id` (webhook lookup)
- `webhook_events.event_id` (idempotency check)
- `audit_logs.created_at DESC` (recent events)

## Applying migrations

### Development (Supabase CLI)
```bash
supabase db push --db-url "postgresql://..."
```

### Production (Supabase Dashboard)
1. Dashboard → SQL Editor
2. Paste and run each migration file in order: 001, 002, … 010
3. Apply `supabase/seed.sql` last

### Reverting migrations
Migrations are not auto-reversible. Write a separate down migration SQL file and apply manually if needed.
